# План поисковика туров через Tourvisor API

## 1. Цель

Создать собственный поисковик туров на странице `/tour-search` с интерфейсом в виде одной компактной строки параметров, как на референсе:

```text
[ Откуда: Сочи ] [ Куда: Турция ] [ Дата вылета: 18 - 25 сен ] [ На сколько: 7 - 10 ночей ] [ Кто едет: 2 взрослых ] [ Найти тур ]
```

Внешний интерфейс и выдача принадлежат Travelio. Tourvisor используется только как поставщик справочников, результатов поиска и данных по конкретным турам.

Документация поставщика: <https://api.tourvisor.ru/search/docs#section/Servis-poiska-turov>

## 2. Важные ограничения API

- Авторизация выполняется JWT-токеном в заголовке `Authorization: Bearer <token>`.
- Токен нельзя передавать во frontend. Все запросы к Tourvisor должны идти через backend-прокси Travelio.
- Поиск асинхронный:
  1. `GET /tours/search` запускает поиск и возвращает `searchId`.
  2. `GET /tours/search/{searchId}/status` возвращает прогресс и статус.
  3. `GET /tours/search/{searchId}?limit=25` возвращает накопленные результаты.
- После запуска нужно показывать уже найденные результаты и периодически обновлять их примерно каждые 3 секунды до завершения поиска.
- Диапазон дат вылета не более 21 дня.
- Диапазон ночей не более 10; допустимые значения `1..28`.
- В одном запросе можно передать не более 3 возрастов детей.
- Старт поиска, продолжение поиска и актуализация авиарейсов учитываются в тарифе. Не запускать поиск на каждое изменение поля формы.
- Ограничение для методов поиска и статуса: до 300 запросов в минуту. Нужны debounce, отмена предыдущих запросов и единый polling-цикл.
- Валюта поиска должна быть ISO-кодом. Поиск в USD/EUR напрямую не поддерживается; для этих сценариев используется код `CU`, если это соответствует настройкам поставщика.

## 3. Первичная строка параметров

### 3.1. Поля, видимые пользователю

| Блок | Подпись | Значение в UI | Данные для API | Обязательность |
|---|---|---|---|---|
| Откуда | `Откуда` | `Сочи` | `departureId` | Обязательно |
| Куда | `Куда` | `Турция` | `countryId` | Обязательно |
| Даты | `Дата вылета` | `18 - 25 сен` | `dateFrom`, `dateTo` | Обязательно |
| Ночи | `На сколько` | `7 - 10 ночей` | `nightsFrom`, `nightsTo` | Обязательно |
| Туристы | `Кто едет` | `2 взрослых` | `adults`, `childs[]` | Обязательно |
| Действие | `Найти тур` | Кнопка | Запуск поиска | - |

Названия отображаются пользователю, но в запрос передаются идентификаторы справочников. Например, `Сочи` хранится как `{ id, name }` и в поиск попадает только `departureId`.

### 3.2. Модель состояния формы

```ts
export type TourSearchForm = {
  departureId: number | null;
  departureName: string;
  countryId: number | null;
  countryName: string;
  dateFrom: string; // YYYY-MM-DD
  dateTo: string; // YYYY-MM-DD
  nightsFrom: number;
  nightsTo: number;
  adults: number;
  childrenAges: number[];
  currency: string;
  onlyCharter: boolean;
  onlyDirect: boolean;
};
```

Начальные значения для первого сценария:

```ts
{
  departureId: null,
  departureName: '',
  countryId: null,
  countryName: '',
  dateFrom: '',
  dateTo: '',
  nightsFrom: 7,
  nightsTo: 10,
  adults: 2,
  childrenAges: [],
  currency: 'RUB',
  onlyCharter: false,
  onlyDirect: false,
}
```

ID города вылета и страны нельзя зашивать в frontend: они должны быть выбраны из актуальных справочников API.

## 4. Справочники и сценарий выбора

Загрузить справочники через backend API и кэшировать их на клиенте с помощью TanStack Query:

1. `GET /departures?departureCountryId=1` — города вылета. Для первого запуска использовать Россию (`1`), но не фиксировать город.
2. `GET /countries?departureId={departureId}` — страны, доступные из выбранного города.
3. `GET /arrivals?departureId={departureId}&onlyCharter=false&onlyDirect=false` — аэропорты/города прилёта. Это поле можно добавить на втором этапе как уточнение внутри страны.
4. `GET /tours/dates?departureId={departureId}&countryId={countryId}` — доступные даты для календаря.
5. `GET /currencies` — список валют; значение по умолчанию зависит от продукта и настроек поставщика.
6. `GET /meals` — типы питания для расширенных фильтров.
7. `GET /regions?countryId={countryId}` — курорты для расширенных фильтров.
8. `GET /operators?departureId={departureId}&countryId={countryId}` — операторы для расширенных фильтров.

Правила зависимостей:

- При изменении `Откуда` сбрасывать `Куда`, дату и связанные справочники.
- При изменении `Куда` перезагружать доступные даты и курорты.
- Не показывать кнопку поиска, пока не выбраны `departureId`, `countryId`, даты и корректные диапазоны ночей.
- Для autocomplete использовать debounce не менее 250-300 мс и не запрашивать справочник на каждый введённый символ, если полный список уже закэширован.

## 5. Backend-прокси

Создать отдельный модуль интеграции, например `backend/src/tourvisor/`:

```text
backend/src/tourvisor/
  tourvisor.module.ts
  tourvisor.controller.ts
  tourvisor.service.ts
  tourvisor.client.ts
  dto/
    tour-search.dto.ts
    tour-search-query.dto.ts
```

### 5.1. Переменные окружения

```env
TOURVISOR_API_BASE_URL=https://api.tourvisor.ru/search
TOURVISOR_JWT_TOKEN=...
TOURVISOR_TIMEOUT_MS=15000
```

Токен хранится только на backend и не возвращается клиенту. Добавить проверку обязательных переменных окружения при старте приложения.

### 5.2. Публичные endpoints Travelio

Названия можно скорректировать под существующие conventions backend, но контракт должен быть похожим на этот:

```text
GET  /api/tour-search/departures
GET  /api/tour-search/countries?departureId=...
GET  /api/tour-search/arrivals?departureId=...&onlyDirect=...
GET  /api/tour-search/dates?departureId=...&countryId=...
GET  /api/tour-search/currencies
POST /api/tour-search/search
GET  /api/tour-search/search/:searchId/status
GET  /api/tour-search/search/:searchId/results?limit=25
GET  /api/tour-search/search/:searchId/continue
GET  /api/tour-search/tours/:tourId?currency=RUB
GET  /api/tour-search/tours/:tourId/flights?currency=RUB
```

`POST /api/tour-search/search` принимает DTO формы, валидирует диапазоны и преобразует его в query-параметры Tourvisor:

```text
GET /tours/search
  departureId=...
  countryId=...
  dateFrom=YYYY-MM-DD
  dateTo=YYYY-MM-DD
  nightsFrom=7
  nightsTo=10
  adults=2
  childs[]=...
  currency=RUB
  onlyCharter=false
  onlyDirect=false
```

Сервис не должен проксировать произвольные query-параметры от клиента. Разрешить только поля из DTO и явным образом преобразовывать массивы.

## 6. Frontend-поток поиска

### Этап A. Первичный поиск

1. Пользователь открывает `/tour-search`.
2. Загружается список городов вылета.
3. Пользователь выбирает город, страну, даты, ночи и состав туристов.
4. Клиент валидирует форму.
5. Кнопка меняется на состояние `Ищем туры...` и блокируется.
6. `POST /api/tour-search/search` возвращает `{ searchId }`.
7. Клиент переходит на состояние результатов, сохраняя строку параметров сверху.

### Этап B. Получение результатов

1. Через 3-5 секунд после запуска запросить статус и первые результаты.
2. Отобразить результаты, которые уже готовы.
3. Пока `status` не завершён, опрашивать статус примерно каждые 3 секунды.
4. При изменении прогресса обновлять выдачу без сброса уже показанных карточек.
5. После завершения остановить polling и показать итоговое количество результатов.
6. При сетевой ошибке показать повтор действия, но не запускать новый поиск автоматически.
7. При уходе со страницы отменять polling и запросы через `AbortController`.

### Этап C. Детали тура

При открытии карточки тура запросить `GET /tours/{tourId}` через backend. Актуализацию авиарейсов (`/tours/{tourId}/flights`) выполнять только перед бронированием или другим подтверждающим действием, а не для каждой карточки выдачи.

## 7. UI-структура

### Первая версия

- Страница `/tour-search` без внешнего Tourvisor-виджета.
- Горизонтальная строка на desktop.
- На мобильном экране строка переходит в вертикальные блоки.
- Поля выглядят как кликабельные сегменты с подписью сверху и текущим значением снизу.
- Кнопка `Найти тур` выделена оранжевым цветом, как в референсе.
- Состояния: загрузка справочников, пустое значение, ошибка, открытый dropdown, disabled, поиск выполняется.
- Доступность: настоящий `button` для действия, `label` для каждого поля, управление dropdown с клавиатуры, видимый focus-state и корректные `aria-expanded`/`aria-controls`.

### Расширенная строка

Не добавлять все фильтры в первичную строку. После запуска поиска предусмотреть панель `Фильтры`:

- курорт/субкурорт;
- аэропорт прилёта;
- питание;
- категория и рейтинг отеля;
- тип отеля;
- услуги отеля;
- туроператор;
- диапазон цены;
- только чартеры;
- только прямые перелёты.

## 8. Типы данных для выдачи

На первом этапе нормализовать ответ Tourvisor в собственный frontend-контракт, чтобы UI не зависел от формы внешнего API:

```ts
export type TourSearchResult = {
  hotelId: number;
  hotelName: string;
  hotelCategory: number;
  hotelRating: number;
  countryName: string;
  regionName: string;
  imageUrl: string | null;
  minPrice: number;
  currency: string;
  tours: Array<{
    id: string;
    date: string;
    nights: number;
    meal: string;
    roomType: string;
    adults: number;
    children: number;
    price: number;
    operatorName: string;
  }>;
};
```

Не считать данные из выдачи окончательной ценой для бронирования без отдельной актуализации авиарейсов и цены.

## 9. Обработка ошибок

Преобразовать ошибки поставщика в понятные ошибки Travelio:

| Ситуация | Поведение |
|---|---|
| Нет JWT или истёк токен | Логировать на backend, пользователю показать временную ошибку сервиса |
| Неверный справочник/ID | `400`, вернуть поле с ошибкой валидации |
| Неверный диапазон дат/ночей | `400`, подсветить соответствующее поле |
| Превышен лимит API | `429`, остановить повторные запросы и предложить повторить позже |
| Ошибка поставщика | `502`, сохранить техническую причину в backend-логах |
| Поиск не завершён | Не считать это ошибкой; показывать прогресс и накопленные результаты |
| Результатов нет | Показать пустое состояние и предложить изменить параметры |

Не логировать JWT, персональные данные и полный URL с чувствительными параметрами.

## 11. Критерии готовности первой версии

- Пользователь выбирает реальный город вылета и страну из справочников.
- Даты и ночи проходят ограничения Tourvisor до отправки запроса.
- В браузере отсутствует JWT Tourvisor.
- Поиск запускается одним действием и возвращает `searchId`.
- Прогресс и накопленные результаты обновляются без перезагрузки страницы.
- Результаты не исчезают при очередном обновлении статуса.
- При пустой выдаче и ошибках пользователь получает понятное состояние.
- Строка поиска соответствует референсу на desktop и остается удобной на мобильном.
- Повторное нажатие не создает несколько параллельных поисков.
- Автоматические запросы к API останавливаются после завершения поиска или ухода со страницы.
