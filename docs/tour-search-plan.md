# План поисковика туров через Tourvisor API

## 1. Цель

Создать собственный поисковик туров на странице `/tour-search` с интерфейсом в виде одной компактной строки параметров, как на референсе:

```text
[ Откуда: Сочи ] [ Куда: Турция ] [ Дата вылета: 18 - 25 сен ] [ На сколько: 7 - 10 ночей ] [ Кто едет: 2 взрослых ] [ Найти тур ]
```

Внешний интерфейс и выдача принадлежат Travelio. Tourvisor используется только как поставщик справочников, результатов поиска и данных по конкретным турам.

Документация поставщика: <https://api.tourvisor.ru/search/docs#section/Servis-poiska-turov>

## 2. Важные ограничения API

- Авторизация выполняется JWT-токеном в заголовке `Authorization: Bearer <token>`.
- Токен нельзя передавать во frontend. Все запросы к Tourvisor должны идти через backend-прокси Travelio.
- Поиск асинхронный:
  1. `GET /tours/search` запускает поиск и возвращает `searchId`.
  2. `GET /tours/search/{searchId}/status` возвращает прогресс и статус.
  3. `GET /tours/search/{searchId}?limit=25` возвращает накопленные результаты.
- После запуска нужно показывать уже найденные результаты и периодически обновлять их примерно каждые 3 секунды до завершения поиска.
- Диапазон дат вылета не более 21 дня.
- Диапазон ночей не более 10; допустимые значения `1..28`.
- В одном запросе можно передать не более 3 возрастов детей.
- Старт поиска, продолжение поиска и актуализация авиарейсов учитываются в тарифе. Не запускать поиск на каждое изменение поля формы.
- Ограничение для методов поиска и статуса: до 300 запросов в минуту. Нужны debounce, отмена предыдущих запросов и единый polling-цикл.
- Валюта поиска должна быть ISO-кодом. Поиск в USD/EUR напрямую не поддерживается; для этих сценариев используется код `CU`, если это соответствует настройкам поставщика.

## 3. Текущее состояние реализации

По состоянию на 14.09.2026 реализован рабочий контур собственного поисковика:

- backend-модуль `backend/src/tourvisor/` проксирует справочники, запуск поиска, статус, результаты, детали тура и рейсы;
- JWT Tourvisor используется только backend-клиентом;
- frontend загружает справочники через `tourSearchApi` и запускает поиск одним действием;
- поиск выполняется асинхронно: после получения `searchId` страница запрашивает статус и накопленные результаты;
- дополнительные фильтры вынесены в сворачиваемую секцию и включают курорт, класс отеля, название/выбор отелей, питание и прямые/чартерные перелёты;
- выбор одного отеля отображает его название, выбор нескольких отображает количество выбранных отелей;
- карточки результатов имеют фиксированную минимальную высоту и защитный fallback для изображения, названия, цены и локации;
- frontend нормализует плоские и несколько распространённых вложенных вариантов ответа Tourvisor перед рендерингом.

Известные ограничения текущей реализации:

- фактический frontend-контракт пока совместим с текущим `TourSearchResult`, но не приведён полностью к целевой модели из раздела 9 с обязательным `hotelId`, `hotelName`, `minPrice` и вложенным массивом `tours`;
- нормализатор ещё нужно расширить для полей, вложенных непосредственно в `hotel`, включая `hotel.country`, `hotel.region`, описания и дополнительные изображения;
- живой поиск может завершиться со статусом `complete` и пустым массивом результатов. Это должно отображаться как понятное пустое состояние, а не как набор визуально пустых карточек;
- полноценная отмена HTTP-запросов через `AbortController`, восстановление поиска из URL и endpoint продолжения поиска ещё не завершены;
- полный frontend typecheck содержит существующие ошибки за пределами изменённого поискового слоя и требует отдельной зачистки.

Новая задача по мультипровайдерности:

- в настройках сайта добавлен ключ `tourProvider` со значениями `tourvisor` и `sletat`;
- значение по умолчанию — `tourvisor`, поэтому существующий поиск не меняет поведение;
- в админской странице настроек добавлен переключатель «Поставщик API»;
- backend проверяет выбранный провайдер перед обращением к поисковому API;
- для `sletat` пока возвращается понятный ответ о том, что адаптер ещё не подключён. Это временное состояние до получения документации, URL, схемы авторизации и тестовых ключей Слетать.ру;
- реализацию Tourvisor удалять или заменять нельзя: она должна стать одним из адаптеров общего контракта поставщиков.

## 4. Первичная строка параметров

### 4.1. Поля, видимые пользователю

| Блок | Подпись | Значение в UI | Данные для API | Обязательность |
|---|---|---|---|---|
| Откуда | `Откуда` | `Сочи` | `departureId` | Обязательно |
| Куда | `Куда` | `Турция` | `countryId` | Обязательно |
| Даты | `Дата вылета` | `18 - 25 сен` | `dateFrom`, `dateTo` | Обязательно |
| Ночи | `На сколько` | `7 - 10 ночей` | `nightsFrom`, `nightsTo` | Обязательно |
| Туристы | `Кто едет` | `2 взрослых` | `adults`, `childs[]` | Обязательно |
| Действие | `Найти тур` | Кнопка | Запуск поиска | - |

Названия отображаются пользователю, но в запрос передаются идентификаторы справочников. Например, `Сочи` хранится как `{ id, name }` и в поиск попадает только `departureId`.

### 4.2. Фактическая модель состояния формы

```ts

  countryId: number | null;
  dateFrom: string; // YYYY-MM-DD
  dateTo: string; // YYYY-MM-DD
  nightsFrom: number;
  nightsTo: number;
  adults: number;
  childs: number[];
  currency: string;
  onlyCharter: boolean;
  onlyDirect: boolean;
  hotelStars: number | null;
  resort: string;
  hotelName: string;
  hotelIds: number[];
  meal: string;
};
```

Начальные значения для первого сценария:

```ts
{
  departureId: null,
  departureName: '',
  countryId: null,
  countryName: '',
  dateFrom: '',
  dateTo: '',
  nightsFrom: 7,
  nightsTo: 10,
  adults: 2,
  childs: [],
  currency: 'RUB',
  onlyCharter: false,
  onlyDirect: false,
  hotelStars: null,
  resort: '',
  hotelName: '',
  hotelIds: [],
  meal: '',

```

ID города вылета и страны нельзя зашивать в frontend: они должны быть выбраны из актуальных справочников API.

## 5. Справочники и сценарий выбора

Загрузить справочники через backend API и кэшировать их на клиенте с помощью TanStack Query:

1. `GET /departures?departureCountryId=1` — города вылета. Для первого запуска использовать Россию (`1`), но не фиксировать город.
2. `GET /countries?departureId={departureId}` — страны, доступные из выбранного города.
3. `GET /arrivals?departureId={departureId}&onlyCharter=false&onlyDirect=false` — аэропорты/города прилёта. Это поле можно добавить на втором этапе как уточнение внутри страны.
4. `GET /tours/dates?departureId={departureId}&countryId={countryId}` — доступные даты для календаря.
5. `GET /currencies` — список валют; значение по умолчанию зависит от продукта и настроек поставщика.
6. `GET /meals` — типы питания для расширенных фильтров.
7. `GET /regions?countryId={countryId}` — курорты для расширенных фильтров.
8. `GET /operators?departureId={departureId}&countryId={countryId}` — операторы для расширенных фильтров.

Правила зависимостей:

- При изменении `Откуда` сбрасывать `Куда`, дату и связанные справочники.
- При изменении `Куда` перезагружать доступные даты и курорты.
- Не показывать кнопку поиска, пока не выбраны `departureId`, `countryId`, даты и корректные диапазоны ночей.
- Для autocomplete использовать debounce не менее 250-300 мс и не запрашивать справочник на каждый введённый символ, если полный список уже закэширован.

## 6. Backend-прокси

Создать отдельный модуль интеграции, например `backend/src/tourvisor/`:

```text
backend/src/tourvisor/
  tourvisor.module.ts
  tourvisor.controller.ts
  tourvisor.service.ts
  tourvisor.client.ts
  dto/
    tour-search.dto.ts
    tour-search-query.dto.ts
```

### 6.1. Переменные окружения

```env
TOURVISOR_API_BASE_URL=https://api.tourvisor.ru/search/api/v1
TOURVISOR_JWT_TOKEN=...
TOURVISOR_TIMEOUT_MS=15000
```

Токен хранится только на backend и не возвращается клиенту. Добавить проверку обязательных переменных окружения при старте приложения.

### 6.2. Публичные endpoints Travelio

Названия можно скорректировать под существующие conventions backend, но контракт должен быть похожим на этот:

```text
GET  /api/tour-search/departures
GET  /api/tour-search/countries?departureId=...
GET  /api/tour-search/arrivals?departureId=...&onlyDirect=...
GET  /api/tour-search/dates?departureId=...&countryId=...
GET  /api/tour-search/currencies
POST /api/tour-search/search
GET  /api/tour-search/search/:searchId/status
GET  /api/tour-search/search/:searchId/results?limit=25
GET  /api/tour-search/tours/:tourId?currency=RUB
GET  /api/tour-search/tours/:tourId/flights?currency=RUB
```

`POST /api/tour-search/search` принимает DTO формы, валидирует диапазоны и преобразует его в query-параметры Tourvisor:

```text
GET /tours/search
  departureId=...
  countryId=...
  dateFrom=YYYY-MM-DD
  dateTo=YYYY-MM-DD
  nightsFrom=7
  nightsTo=10
  adults=2
  childs[]=...
  currency=RUB
  onlyCharter=false
  onlyDirect=false
```

Сервис не должен проксировать произвольные query-параметры от клиента. Разрешить только поля из DTO и явным образом преобразовывать массивы.

Текущий backend DTO принимает обязательные `departureId`, `countryId`, даты, диапазон ночей, взрослых и валюту. Дополнительно принимает `childs`, `onlyCharter`, `onlyDirect`, `hotelStars`, `resort`, `hotelName`, `meal` и `hotelIds`.

Текущий mapping в `TourvisorService` преобразует расширенные параметры в `hotelCategory`, `regionIds`, `meal` и `hotelIds`. Название отеля при необходимости предварительно разрешается в список ID через справочник `/hotels`.

Проверки диапазонов дат и ночей реализованы в сервисе. Параметр `limit` результатов валидируется как положительное целое с default `25`.

### 6.3. Мультипровайдерная архитектура

Текущий `TourvisorService` временно выполняет роль адаптера Tourvisor и проверяет настройку `tourProvider`. Следующий шаг — вынести общий контракт в отдельные типы и сервис выбора:

```ts
export type TourProviderId = 'tourvisor' | 'sletat';

export interface TourProvider {
  getDepartures(query: ReferenceQueryDto): Promise<unknown>;
  getCountries(query: ReferenceQueryDto): Promise<unknown>;
  getDates(query: ReferenceQueryDto): Promise<unknown>;
  startSearch(search: TourSearchDto): Promise<{ searchId: number | string }>;
  getStatus(searchId: number | string): Promise<unknown>;
  getResults(searchId: number | string, limit: number): Promise<unknown>;
  getTour(tourId: number | string, currency: string): Promise<unknown>;
}
```

После получения документации создать `SletatProvider`, не меняя публичный frontend-контракт. `TourProviderResolver` должен выбирать реализацию по `tourProvider`, а не по параметру, который может прислать пользователь в запросе. До регистрации рабочего `SletatProvider` выбор `sletat` должен оставаться явно недоступным для поиска и не должен молча отправлять запросы в Tourvisor.

Для каждого провайдера отдельно определить:

- base URL, способ авторизации и срок действия ключей;
- справочники и соответствие ID стран, курортов, отелей и питания;
- запуск асинхронного поиска, polling, лимиты и пагинацию;
- модель результата и mapping в общий контракт Travelio;
- детали тура, актуализацию цены/рейсов и ограничения тарификации;
- кэширование, rate limits, таймауты и правила обработки ошибок.

### 6.4. Подтверждённый контракт Слетать.ру

Для базового шлюза поиска используется JSON API:

```text
https://module.sletat.ru/Main.svc/{MethodName}
```

Документация описывает авторизацию логином и паролем личного кабинета. Поисковый запрос, получение его состояния и загрузка результатов должны выполняться с одного IP-адреса. Ключи и пароль должны храниться только на backend в отдельных переменных окружения, например `SLETAT_LOGIN` и `SLETAT_PASSWORD`.

Справочники базового шлюза: `GetDepartCities`, `GetCountries`, `GetCities`, `GetHotels`, `GetHotelStars`, `GetMeals`, `GetTourOperators`, `GetTourDates` и `GetAvailableFeatures`. Они покрывают города вылета, страны, курорты, отели, категории, питание, операторов, даты и услуги отеля.

Поиск выполняется не так, как текущий Tourvisor polling:

1. `GetTours` без `requestId` создаёт запрос и возвращает `requestId`.
2. Состояние запрашивается только через `GetLoadState`; использовать `GetTours` для polling запрещено условиями шлюза.
3. Между вызовами `GetLoadState` нужна пауза не менее 1,5 секунды; в приложении нужен внутренний общий timeout, чтобы исключить бесконечный цикл.
4. По завершении или при наличии первых результатов повторно вызывается `GetTours` с `requestId`, `updateResult=1`, `pageSize` и `pageNumber`.
5. Слетать.ру не хранит результаты длительное время, поэтому backend должен сохранять накопленный результат поисковой сессии локально.

Минимальные параметры `GetTours`, которые потребуются в адаптере:

```text
login, password,
cityFromId, countryId,
s_adults, s_kids, s_kids_ages,
s_nightsMin, s_nightsMax,
s_departFrom, s_departTo,
currencyAlias,
cities, stars, meals, hotels,
requestId, pageSize, pageNumber, updateResult
```

Provider-specific ограничения: `s_departFrom`/`s_departTo` используют формат `DD/MM/YYYY`, допустимый диапазон дат — до 45 дней; в одном запросе допускается не более 10 отелей и есть ограничения отдельных туроператоров на количество курортов. Это нужно валидировать в Sletat adapter, не меняя общий DTO Tourvisor.

Ответ `GetTours` содержит обёртку `GetToursResult`, внутри `Data.aaData`. Элемент `aaData` — позиционный массив, а не объект. Для общего контракта нужно явно описать mapping минимум таких позиций: `offerId`, `sourceId`, `hotelId`, название отеля, категория, курорт, питание, размещение, даты, ночи, цена, валюта, URL изображения, рейтинг, описание и архивный hash. Нельзя передавать этот массив напрямую во frontend.

Для цен использовать числовые поля результата, когда они доступны, а не парсить только строку вида `30233 RUB`. В mapping сохранить исходную цену, полную цену со сборами и валюту. Любая цена из поиска считается предварительной.

Перед показом финальных деталей или переходом к бронированию использовать `ActualizePrice`: метод принимает `sourceId`, `offerId` и `requestId`, проверяет билеты, места, топливные/визовые сборы и может вернуть дополнительные ресурсы. Его ответ также требует отдельного нормализатора.

### 6.5. Расширения и лицензии Слетать.ру

По публичной странице шлюзов указаны ориентировочные цены «от», которые нужно подтвердить договором и коммерческим предложением:

| Расширение | Назначение | Публичная информация |
|---|---|---|
| базовый шлюз поиска туров | справочники, поиск, выдача | от 15 000 руб. |
| данные о туроператорах | название оператора и ссылка на его тур | от 30 000 руб. |
| детальная актуализация | перелёты, доплаты, подробности и ресурсы тура | от 1 000 руб. |
| отельная база | описания, фотографии, услуги, координаты и отзывы | по запросу |
| онлайн-оплата | заявки и платёжный redirect через SOAP/WSDL | указана как бесплатная, условия подтвердить |

Базовый поиск может вернуть данные без полного описания отеля. Поэтому карточки и страница деталей должны уметь работать в двух режимах: только данные `GetTours` и расширенные данные после `ActualizePrice`/отельной базы. Контент `Description`, отзывы и фотографии Слетать.ру имеют отдельные лицензионные ограничения; до использования в SEO, кэшировании и изменения текста нужно проверить договор.

Аналитика цен (`graph.sletat.ru`) является отдельным необязательным контуром и не входит в первый этап подключения поиска. Её можно добавить позже для графика минимальных цен по датам и истории изменения цены по `TourArchiveHash`.

## 7. Frontend-поток поиска

### Этап A. Первичный поиск

1. Пользователь открывает `/tour-search`.
2. Загружается список городов вылета.
3. Пользователь выбирает город, страну, даты, ночи и состав туристов.
4. Клиент валидирует форму.
5. Кнопка меняется на состояние `Ищем туры...` и блокируется.
6. `POST /api/tour-search/search` возвращает `{ searchId }`.
7. Клиент переходит на состояние результатов, сохраняя строку параметров сверху.

### Этап B. Получение результатов

1. Через 3-5 секунд после запуска запросить статус и первые результаты.
2. Отобразить результаты, которые уже готовы.
3. Пока `status` не завершён, опрашивать статус примерно каждые 3 секунды.
4. При изменении прогресса обновлять выдачу без сброса уже показанных карточек.
5. После завершения остановить polling и показать итоговое количество результатов.
6. При сетевой ошибке показать повтор действия, но не запускать новый поиск автоматически.
7. При уходе со страницы polling очищается и новые циклы не запускаются; передачу `AbortSignal` в axios/fetch ещё нужно довести отдельно.

### Этап C. Детали тура

При открытии карточки тура запросить `GET /tours/{tourId}` через backend. Актуализацию авиарейсов (`/tours/{tourId}/flights`) выполнять только перед бронированием или другим подтверждающим действием, а не для каждой карточки выдачи.

В административной странице «Настройки сайта» отображать select/segmented control:

- `Tourvisor` — текущий рабочий вариант и значение по умолчанию;
- `Слетать.ру` — показывать как подготовленный вариант до завершения интеграции или блокировать выбор до появления адаптера;
- при сохранении валидировать значение на backend;
- после изменения сбрасывать кэш публичных настроек и использовать новый выбор для следующих поисков;

- при недоступном адаптере показывать пользователю понятное состояние сервиса, а не пустую выдачу.

## 9. Типы данных для выдачи

Целевой контракт остаётся следующим, но текущий код пока использует совместимый переходный тип с полями `id`, `name`, `price`, `picturelink`, `country`, `region`, `meal`, `roomType`, `tourid`/`tourId` и дополнительными полями отеля:

```ts
export type TourSearchResult = {
  hotelId: number;
  hotelName: string;
  hotelCategory: number;
  hotelRating: number;
  countryName: string;
  regionName: string;
  imageUrl: string | null;
  minPrice: number;
  currency: string;
  tours: Array<{
    id: string;
    date: string;
    nights: number;
    meal: string;
    roomType: string;
    adults: number;
    children: number;
    price: number;
    operatorName: string;
  }>;
};
```

Текущий нормализатор поддерживает значения цены строкой или числом, несколько вариантов изображений и вложенные коллекции результатов (`items`, `results`, `data`, `offers`, `tours`). Нужно добавить чтение `hotel.country`, `hotel.region`, `hotel.name`, `hotel.images` и аналогичных вариантов с нечувствительностью к регистру ключей.

Не считать данные из выдачи окончательной ценой для бронирования без отдельной актуализации авиарейсов и цены.

## 10. Обработка ошибок

Преобразовать ошибки поставщика в понятные ошибки Travelio:

| Ситуация | Поведение |
|---|---|
| Нет JWT или истёк токен | Логировать на backend, пользователю показать временную ошибку сервиса |
| Неверный справочник/ID | `400`, вернуть поле с ошибкой валидации |
| Неверный диапазон дат/ночей | `400`, подсветить соответствующее поле |
| Превышен лимит API | `429`, остановить повторные запросы и предложить повторить позже |
| Ошибка поставщика | `502`, сохранить техническую причину в backend-логах |
| Поиск не завершён | Не считать это ошибкой; показывать прогресс и накопленные результаты |
| Результатов нет | Показать пустое состояние и предложить изменить параметры |

Отдельно обработать случай `status=complete` и `results=[]`: не показывать карточки-заглушки, а вывести сообщение, что по выбранным параметрам предложений не найдено, с действием изменения фильтров.

Не логировать JWT, персональные данные и полный URL с чувствительными параметрами.

## 12. Критерии готовности первой версии

- Пользователь выбирает реальный город вылета и страну из справочников.
- Даты и ночи проходят ограничения Tourvisor до отправки запроса.
- В браузере отсутствует JWT Tourvisor.
- Поиск запускается одним действием и возвращает `searchId`.
- Прогресс и накопленные результаты обновляются без перезагрузки страницы.
- Результаты не исчезают при очередном обновлении статуса.
- При пустой выдаче и ошибках пользователь получает понятное состояние.
- Строка поиска соответствует референсу на desktop и остается удобной на мобильном.
- Повторное нажатие не создает несколько параллельных поисков.
- Автоматические запросы к API останавливаются после завершения поиска или ухода со страницы.

Дополнительный критерий перед завершением текущей задачи: карточка должна отображать название, страну/курорт, изображение, питание, тип номера и цену для каждого реально пришедшего результата; при `[]` должна отображаться пустая выдача без пустых карточек.

Для мультипровайдерного режима дополнительно:

- администратор может выбрать поставщика в настройках сайта;
- при `tourvisor` текущий поиск работает без регрессии;
- при `sletat` до подключения адаптера отображается контролируемая ошибка «поставщик ещё не подключён»;
- после подключения Sletat API один и тот же frontend использует общий контракт и не знает provider-specific поля;
- ключи обоих поставщиков отсутствуют в браузере и логах с чувствительными параметрами.
