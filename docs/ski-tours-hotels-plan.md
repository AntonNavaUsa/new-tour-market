# План раздела «Горнолыжные туры»

## 1. Цель

Создать раздел с горнолыжными турами, где карточки отображаются динамически на основе картотеки отелей. На первом этапе картотека должна содержать минимально необходимые данные:

- название;
- тип размещения;
- звездность;
- описание;
- признак `ski-in/ski-out`;
- одну или несколько локаций из существующего справочника.

Администратор управляет отелями через CRUD, а пользователь видит каталог с фильтрами и карточками, собранными из данных отеля.

## 2. Архитектурное решение

В проекте уже есть сущность `Accommodation`, которая используется в карточках туров и связана с фото, отзывами, блокировками дат и ролями доступа. Поэтому отдельную таблицу `Hotel` на MVP создавать не следует: это приведет к дублированию данных и параллельным CRUD/API.

Рекомендуемый вариант:

1. Расширить `Accommodation` полями, специфичными для гостиницы:
   - `stars` — целое число от 0 до 5, nullable для неотельных объектов;
   - `skiInSkiOut` — Boolean, по умолчанию `false`.
2. Добавить связь `Accommodation` с `Location` через явную промежуточную таблицу `AccommodationLocation`.
3. Использовать `Accommodation.type = HOTEL` для гостиниц. При необходимости на первом этапе разрешить и другие типы размещения, но в горнолыжном каталоге фильтровать их явно.
4. Не создавать полноценный `Card` тура на каждый отель автоматически. Сначала формировать публичную read-модель/проекцию горнолыжного предложения. Обычная `Card` должна появляться только после появления параметров тура: цены, дат, программы, включенных услуг и условий бронирования.

Это разделяет каталог отелей и продаваемый туристический продукт: один отель может участвовать в нескольких предложениях.

## 3. Изменения в базе данных

### 3.1. `Accommodation`

Добавить:

```text
stars          Int?
skiInSkiOut    Boolean @default(false)
```

Для `stars` установить ограничение на уровне DTO и сервиса: допустимы значения `0..5`. Значение `null` означает, что звездность не указана. Не следует подменять неизвестную звездность нулем.

Текстовое поле `description` уже есть и подходит для краткого описания отеля. Поле `name` уже есть. Поле `type` уже использует `AccommodationType` и содержит `HOTEL`.

### 3.2. `AccommodationLocation`

Создать явную M:N-связь:

```text
AccommodationLocation {
  accommodationId -> Accommodation
  locationId      -> Location

  primary key (accommodationId, locationId)
}
```

Рекомендуемые правила:

- удаление отеля удаляет его связи с локациями (`onDelete: Cascade`);
- удаление локации запрещено или требует предварительного отвязывания, чтобы случайно не изменить каталог;
- порядок локаций не нужен для фильтрации, но при необходимости можно добавить `isPrimary` или `sortOrder` отдельной задачей;
- один отель может быть привязан к нескольким существующим локациям, например `Красная Поляна`, `Высота 960`, `Роза Хутор 560`.

Индексы:

- уникальный составной ключ `(accommodationId, locationId)`;
- индекс по `locationId`;
- индекс по `skiInSkiOut` и, при необходимости, по `stars` после появления заметного объема данных.

### 3.3. Миграция и данные

1. Добавить поля в Prisma schema и создать миграцию.
2. Для существующих записей `Accommodation` выставить `skiInSkiOut = false`, `stars = null`.
3. Не назначать существующим объектам локации автоматически по адресу: это может создать неверные связи.
4. Добавить seed-примеры минимум с одним отелем, несколькими локациями и одним отелем без `ski-in/ski-out` для проверки фильтрации.
5. Проверить миграцию на копии production-структуры до выкладки.

## 4. CRUD отелей

Использовать существующий `AccommodationsModule` и текущий endpoint `/api/accommodations`. В UI можно назвать раздел «Отели», а внутри API сохранить общее имя `accommodations`, чтобы не ломать текущих потребителей.

### 4.1. Создание

`POST /api/accommodations`

Минимальное тело:

```json
{
  "name": "Отель",
  "type": "HOTEL",
  "stars": 4,
  "description": "Описание отеля",
  "skiInSkiOut": true,
  "locationIds": ["location-id-1", "location-id-2"]
}
```

Проверки:

- `name` обязательно и очищается от лишних пробелов;
- `type` должен быть значением enum;
- `stars` — целое число `0..5` или `null`;
- все `locationIds` должны существовать;
- дубликаты `locationIds` нужно удалять или отклонять единообразно;
- для раздела горнолыжных туров объект с `type != HOTEL` не должен попадать в выдачу отелей.

### 4.2. Чтение и обновление

`GET /api/accommodations/:id` должен возвращать:

- основные поля;
- список локаций с `id`, названием и данными, необходимыми для отображения;
- фотографии;
- отзывы, если они уже используются на странице размещения.

`PATCH /api/accommodations/:id` должен обновлять основные поля и синхронизировать `locationIds` в транзакции. Семантика `locationIds` — полный актуальный список: переданный массив заменяет прежние связи; отсутствие поля означает «не менять».

### 4.3. Удаление и доступ

Сохранить текущую ролевую модель `ADMIN`, `PARTNER`, `HOTEL_OWNER`, но явно определить владельца записи:

- `ADMIN` может видеть и изменять все отели;
- `PARTNER` и `HOTEL_OWNER` могут изменять только разрешенные им записи;
- публичные GET не должны раскрывать служебные поля владельца.

Перед удалением проверить, используется ли отель в существующих карточках. Для MVP предпочтительнее архивирование/soft delete, если физическое удаление может нарушить опубликованные предложения. Если soft delete пока не вводится, DELETE должен возвращать понятную ошибку при наличии связей с опубликованными карточками.

## 5. Фильтры отображения

### 5.1. Публичный список горнолыжных отелей

Рекомендуемый endpoint:

`GET /api/ski-tours/hotels`

Он может быть отдельным facade-endpoint поверх `AccommodationsService`, чтобы публичный раздел не зависел от универсальной выдачи размещений.

Параметры:

- `skiInSkiOut=true|false` — фильтр по признаку ski-in/ski-out;
- `locationIds=...` или повторяющийся `locationId=...` — фильтр по одной или нескольким локациям;
- `stars=3,4,5` — опциональный фильтр по звездности;
- `type=HOTEL` — фиксируется сервером для этого endpoint;
- `search` — поиск по названию, если нужен на админском и публичном экране;
- `page` и `limit` либо существующие `skip` и `take`.

Правило для нескольких локаций нужно зафиксировать в API:

- по умолчанию `OR`: отель подходит, если связан хотя бы с одной выбранной локацией;
- для строгого поиска по всем выбранным локациям добавить `locationMode=all` только при реальной потребности.

Для первого релиза достаточно `OR`: он соответствует пользовательскому ожиданию при выборе нескольких соседних курортных зон.

Фильтр `skiInSkiOut=true` возвращает только отели с `skiInSkiOut = true`. При отсутствии параметра показываются оба варианта. Не следует трактовать отсутствие признака как `true`.

### 5.2. Источник вариантов фильтра

`GET /api/locations` уже должен использовать существующий справочник локаций. Для раздела можно добавить:

`GET /api/ski-tours/hotels/filter-options`

Ответ:

- доступные локации, которые назначены хотя бы одному отелю;
- доступные значения звездности;
- количество результатов для каждого варианта, если это понадобится интерфейсу.

Список вариантов не должен быть захардкожен во frontend: названия и slug берутся из `Location`.

## 6. Динамические карточки раздела

Карточка отеля в разделе «Горнолыжные туры» должна строиться из read-модели, например:

```text
id
name
type
stars
description
skiInSkiOut
locations[]
coverPhoto
rating/reviewsCount
```

На MVP карточка содержит ссылку на страницу отеля/предложения и не обещает бронирование тура, если еще нет цены и доступности.

### Следующий слой для настоящей карточки тура

Когда появятся коммерческие параметры, добавить отдельную сущность предложения, например `SkiTourOffer`, связав ее с `Accommodation`:

- отель;
- даты или период действия;
- длительность;
- цена и тип цены;
- трансфер/ски-пасс/питание;
- программа и включенные услуги;
- статус публикации;
- ссылка на бронирование или связь с существующей `Card`.

Один отель может иметь несколько таких предложений. Генерация должна быть детерминированной: изменение описания отеля обновляет карточку, но не создает дубликат предложения.

## 7. Админский интерфейс

Добавить раздел «Отели» с таблицей:

- название;
- тип;
- звездность;
- `ski-in/ski-out`;
- локации;
- количество связанных карточек/предложений;
- дата обновления;
- действия: открыть, изменить, архивировать.

Форма отеля:

- название;
- тип размещения;
- звездность через select/stepper с вариантами `не указано`, `1..5`;
- textarea для описания;
- checkbox/toggle `Ski-in / ski-out`;
- мультиселект локаций из справочника;
- существующее управление фотографиями.

Фильтры админской таблицы должны использовать те же признаки, что и публичная выдача: поиск, тип, звездность, ski-in/ski-out, локации.

## 8. Тестирование и приемка

### Backend

- создание отеля с одной локацией;
- создание отеля с несколькими локациями;
- обновление полного списка `locationIds` в транзакции;
- валидация звездности `-1`, `6`, дробного и строкового значения;
- фильтр `skiInSkiOut=true`;
- фильтр по одной локации;
- фильтр по нескольким локациям с правилом `OR`;
- отсутствие несуществующих локаций;
- проверка прав `ADMIN`, `PARTNER`, `HOTEL_OWNER`;
- исключение неотелей из `/api/ski-tours/hotels`;
- корректное поведение при удалении отеля, связанного с карточкой.

### Frontend

- создание и редактирование отеля;
- сохранение нескольких локаций;
- сброс фильтров;
- совместное применение ski-in/ski-out и локации;
- корректное отображение пустой выдачи;
- отображение `не указано` для nullable-звездности;
- мобильное отображение карточек и фильтров.

### Definition of Done для MVP

- миграция применена на чистой БД;
- CRUD работает с несколькими локациями;
- публичная выдача возвращает только `HOTEL`;
- оба заявленных фильтра работают и покрыты тестами;
- существующие карточки и календарь размещений продолжают работать;
- документация Swagger обновлена;
- добавлены seed-данные для ручной проверки.

## 9. Этапы реализации

1. Уточнить бизнес-правила звездности, архивирования и доступа партнеров.
2. Расширить Prisma schema и добавить миграцию.
3. Добавить DTO, валидацию, M:N-синхронизацию и фильтры в backend.
4. Добавить backend-тесты на CRUD и фильтрацию.
5. Сделать админский список и форму отеля.
6. Сделать публичный endpoint и каталог горнолыжных отелей.
7. Подключить фотографии и существующие отзывы к read-модели карточки.
8. Добавить seed и выполнить приемку по чек-листу.
9. Отдельно спроектировать коммерческую сущность `SkiTourOffer`, когда появятся цены, даты и состав тура.

## 10. Вопросы, требующие решения

1. Под «типом» понимается текущий тип размещения (`HOTEL`, `HOSTEL`, `APARTMENT` и т. п.) или отдельная классификация отеля: апарт-отель, шале, резорт?
Ответ: текущий тип
2. Звездность должна быть только `1..5` или допустимы значения `0`/«без звезд»?
Ответ: допустимо без звезд
3. Нужен ли отдельный статус `архивирован`, чтобы не удалять отели, связанные со старыми турами?
Ответ: да
4. Должен ли `ski-in/ski-out` быть одним Boolean-признаком или нужны два признака: `skiIn` и `skiOut`?
Ответ: один признак
5. Что именно должно появляться в карточке «тура» кроме данных отеля: цена, даты, длительность, трансфер, ски-пасс, питание?
Ответ: пока оставим это на будущее
6. Для нескольких выбранных локаций достаточно правила «подходит любая» (`OR`) или нужен поиск «подходит всем» (`AND`)?
Ответ: OR
7. Должны ли партнеры видеть и редактировать общую картотеку, или отели создает и изменяет только администратор?
Ответ: только администратор
